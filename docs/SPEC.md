## 1. 목표

사내 시설 · 장비 고장을 누구나 바로 신고하고, 시설팀이 사람이 다칠 수 있는 고장부터 처리한다.

## 2. 사용자와 사용자 스토리

| 누가 | 하는 일 |
|---|---|
| 직원 (누구나) | 고장을 보면 신고함. 이름은 신고 칸에 직접 씀 |
| 시설팀 | 신고를 급한 순으로 보고, 담당자를 정하고, 끝나면 완료 처리함 |

- **로그인이 없습니다.** 화면 하나에서 누구나 신고하고 누구나 처리합니다. (8절 범위 밖)
- 시설팀 담당자 4명: 전기 **이주임** · 공조 **최대리** · IT기기 **정사원** · 건물 **한과장**

### 사용자 스토리

- **US-01**: 시설팀으로서, 신고를 급한 순으로 보고 싶다. 왜냐하면 사람이 다칠 수 있는 고장부터 처리해야 하니까.
- **US-02**: 시설팀으로서, 신고를 상태별로 걸러 보고 싶다. 왜냐하면 아직 아무도 맡지 않은 신고가 몇 건인지 바로 알아야 하니까.
- **US-03**: 직원으로서, 로그인 없이 제목 · 장소 · 이름만 쓰고 바로 신고하고 싶다. 왜냐하면 고장을 본 그 자리에서 알려야 하니까.
- **US-04**: 시설팀으로서, 신고에 담당자를 정하고 끝나면 완료 처리하고 싶다. 왜냐하면 누가 맡았고 무엇이 끝났는지 모두가 알아야 하니까.
- **US-05**: 시설팀으로서, 서버를 다시 켜도 신고가 남아 있기를 원한다. 왜냐하면 신고가 사라지면 고장이 그대로 방치되니까.

─────────────────────────────────────────────────────────────
 [ 전체 40 ]  [ 접수 25 ]  [ 배정 10 ]  [ 완료 5 ]

  ...

### 화면 규칙

| 무엇 | 규칙 |
|---|---|
| 심각도 배지 | 긴급 = 빨강 · 주의 = 주황 · 정보 = 회색 · 미분류 = 회색 점선 테두리 (4절) |
| 상태 배지 | 접수 = 파랑 · 배정 = 노랑 · 완료 = 초록 |
| 카드 순서 | 서버가 준 순서 그대로 (서버가 급한 순으로 줌 · 5절) |
| 카드 아래쪽 | 접수 상태면 담당 고르기 칸 · 배정 상태면 "담당: 이름"과 [완료] 버튼 · 완료 상태면 "담당: 이름"만 |
| 담당 고르기 | 2절의 담당자 4명 중 하나 |
| 상태 탭 | 누르면 그 상태만 보임 · 탭마다 건수 · 세 탭 건수의 합 = 전체 |
| 신고 후 | 신고 칸을 비우고 목록을 다시 불러옴 · 새 신고는 '미분류 · 접수'로 보임 |
| 오류 | 서버가 400을 주면 신고 칸 바로 아래에 서버가 보낸 문장을 빨간 글씨로 보여 줌 |
| 건물 | 사무동(office) · 생산동(plant) 중 고름 · 기본은 사무동 |

## 4. 심각도 기준

신고자는 심각도를 고르지 않습니다. 접수되면 '미분류'이고, 시설팀(8일차 M1부터는 AI 제안 + 사람 승인)이 정합니다.

| 심각도 | 코드 | 기준 | 예 |
|---|---|---|---|
| 긴급 | `urgent` | 사람이 다칠 수 있음 | 천장 누수 · 타는 냄새 · 콘센트 스파크 · 비상구 막힘 |
| 주의 | `warning` | 업무가 멈춤 | 회의 직전 프로젝터 고장 · 출입 카드 인식 안 됨 · 층 전체 와이파이 끊김 |
| 정보 | `info` | 불편함 | 토너 부족 · 의자 바퀴 고장 · 형광등 깜빡임 |
| 미분류 | `none` | 아직 아무도 안 정함 | 접수 직후 |

## 5. API (화면과 서버의 약속)

모든 주소는 `/api/`로 시작하고, 주고받는 값은 JSON입니다.

- 서버(`src/server.js`)는 **`PORT` 환경변수(없으면 8080)**로 켜지고, 같은 서버가 화면(`src/public/index.html`)도 내어 줍니다 → http://localhost:8080
- `npm test`는 서버를 `DB_MODE=memory`로 직접 켜서 이 약속을 확인합니다. 그래서 서버가 `PORT`와 `DB_MODE`를 따라야 테스트가 돕니다.

| 하는 일 | 주소 | 보내는 값 | 성공하면 | 실패하면 |
|---|---|---|---|---|
| 목록 보기 | `GET /api/reports` · `GET /api/reports?status=open` | `status`는 선택 (`open` · `assigned` · `resolved`) · 없으면 전체 | **200** + 신고 배열 (급한 순) | 목록에 없는 `status` 값이면 **200** + 빈 배열 `[]` |
| 신고하기 | `POST /api/reports` | `title` · `location` · `reporter_name` (필수) / `building` · `asset_id` · `body` (선택) | **201** + 방금 만든 신고 (`status: "open"` · `severity: "none"`) | 규칙에 안 맞으면 **400** |
| 처리하기 | `PATCH /api/reports/:id` | `assignee` · `status` · `severity` 중 하나 이상 | **200** + 바뀐 신고 | 규칙에 안 맞으면 **400** · 없는 번호면 **404** |

### 입력 규칙 (서버가 검사 · 화면에서만 막는 것은 검사가 아님)

| 칸 | 규칙 |
|---|---|
| `title` 제목 | 앞뒤 빈칸을 뺀 뒤 1~100자 · 없으면 400 "제목을 입력하세요" |
| `location` 장소 | 앞뒤 빈칸을 뺀 뒤 1~50자 · 없으면 400 "장소를 입력하세요" |
| `reporter_name` 이름 | 앞뒤 빈칸을 뺀 뒤 1~20자 · 없으면 400 "이름을 입력하세요" |
| `building` 건물 | `office` 또는 `plant` · 없으면 `office` |
| `asset_id` 설비 번호 | 20자 이하 · 없으면 빈칸 |
| `body` 내용 | 1000자 이하 · 없으면 빈칸 |
| `assignee` 담당자 | 2절의 담당자 4명 중 하나 · **담당자를 정하면 상태는 자동으로 `assigned`** |
| `status` 상태 | `open` · `assigned` · `resolved` 중 하나 · 그 밖의 값은 400 |
| `severity` 심각도 | `urgent` · `warning` · `info` 중 하나 · 그 밖의 값은 400 (M2 미션 ② · 10.3절) |

### 정렬 규칙 (목록)

심각도 **긴급 → 주의 → 정보 → 미분류**, 같은 심각도 안에서는 **먼저 들어온 신고(번호가 작은 것)부터**.

### 오류 응답 모양 (모든 실패가 같은 모양)

```json
{ "error": { "code": "BAD_INPUT", "message": "제목을 입력하세요" } }
```

| 상황 | 코드 | `code` |
|---|---|---|
| 입력 규칙 위반 | 400 | `BAD_INPUT` |
| 없는 번호 | 404 | `NOT_FOUND` |
| 없는 API 주소 | 404 | `NOT_FOUND` |
| 서버 안에서 난 오류 | 500 | `SERVER_ERROR` (자세한 내용은 서버 터미널에만) |

## 6. 데이터 (테이블 설계)

테이블은 `reports` 하나입니다. 테이블을 만드는 SQL은 DB마다 문법이 조금 달라서 같은 이름으로 두 개를 둡니다: `src/migrations/supabase/001_reports.sql` · `src/migrations/sqlite/001_reports.sql`.

| 칸 | 뜻 | 필수 | 기본값 | 규칙 |
|---|---|---|---|---|
| `id` | 신고 번호 | 자동 | 1부터 차례로 | 고유 |
| `title` | 제목 | ✓ | — | 1~100자 |
| `body` | 내용 | | 빈칸 | |
| `location` | 장소 | ✓ | — | 1~50자 |
| `building` | 건물 | ✓ | `office` | `office` · `plant` 중 하나 |
| `asset_id` | 설비 번호 | | 빈칸 | 예: `PR-3F-02` |
| `reporter_name` | 신고자 이름 | ✓ | — | 1~20자 |
| `severity` | 심각도 | ✓ | `none` | `urgent` · `warning` · `info` · `none` 중 하나 |
| `category` | 유형 | ✓ | `none` | `ELECTRIC`(전기) · `HVAC`(공조) · `IT_DEVICE`(IT기기) · `BUILDING`(건물) · `none` 중 하나 |
| `status` | 상태 | ✓ | `open` | `open`(접수) · `assigned`(배정) · `resolved`(완료) 중 하나 |
| `assignee` | 담당자 | | 빈칸 | 2절의 4명 중 하나 |
| `severity_by` | 심각도를 정한 주체 | | 빈칸 | `''` · `ai` · `human` 중 하나 · 서버만 정함 (10.5절 · 8일차 M2) |
| `created_at` | 신고 시각 | ✓ | 지금 | |

- **"중 하나" 규칙은 DB에도 겁니다**(CHECK 제약). 서버 검사를 빠져나간 값도 DB가 한 번 더 막습니다.
- 처음 켤 때 `data/seed.json`의 신고 40건을 넣습니다 (사무동 30 · 생산동 10 / 심각도가 정해진 20건 + 미분류 20건).
- **DB는 `.env`의 `DB_MODE`로 고릅니다.** `src/db.js` 하나만 이 차이를 압니다. 나머지 파일은 DB가 무엇인지 모릅니다.

| `DB_MODE` | 어디에 저장 | 테이블 만들기 | 누가 DB에 들어오나 |
|---|---|---|---|
| `supabase` (기본) | 7일차에 만든 Supabase 프로젝트 | `src/migrations/supabase/001_reports.sql`을 SQL Editor에 붙여 넣고 Run · 시드 40건은 서버가 처음 켤 때 넣음 | **RLS는 켜고 정책은 두지 않음** → `.env`의 서버 전용 키(`SUPABASE_SECRET_KEY`)를 가진 `src/server.js`만 |
| `sqlite` (사내 방식) | `data/app.db` 파일 하나 | 서버가 켜질 때 `src/migrations/sqlite/`를 자동 실행 (한 번 실행한 파일은 다시 안 함) | 서버만 파일을 읽음 |
| `memory` (테스트용) | 서버 메모리 (껐다 켜면 처음으로) | 시드 40건을 배열로 | 테스트만 씀 · 진짜 DB를 건드리지 않음 |

## 7. 인수 기준 (Given / When / Then)

괄호 안은 그 기준을 확인하는 방법입니다. `tests/api.test.js`의 테스트 이름이 그대로 체크리스트입니다.

### AC-01 목록 (US-01)
- Given: 신고 40건이 있을 때
- When: 화면을 열면
- Then: 카드 40장이 긴급 → 주의 → 정보 → 미분류 순으로, 제목 · 장소 · 신고자 · 시각 · 심각도 배지 · 상태 배지와 함께 보인다
- (테스트: "목록은 40건을 긴급 → 주의 → 정보 → 미분류 순으로 준다")

### AC-02 상태 필터 (US-02)
- Given: 접수 · 배정 · 완료 신고가 섞여 있을 때
- When: [접수] 탭을 누르면
- Then: 접수 카드만 보이고, 탭마다 건수가 보이며 세 탭 건수의 합은 전체 건수와 같다
- (테스트: "상태 필터: open만 고르면 open만 온다" · "필터에 이상한 값(SQL 인젝션 문자열)을 넣어도 0건")

### AC-03 신고 (US-03)
- Given: 신고 칸에서
- When: 제목 · 장소 · 이름을 쓰고 [신고]를 누르면
- Then: 목록에 '미분류 · 접수' 카드로 추가된다. 제목이나 장소를 비운 채 누르면 추가되지 않고 "제목을 입력하세요" / "장소를 입력하세요"가 신고 칸 아래에 보인다
- (테스트: "신고 등록 → 201 · '접수' · 이름이 남는다" · "제목이 비면 400" · "장소가 비면 400")

### AC-04 처리 (US-04)
- Given: 상태가 '접수'인 카드에서
- When: 담당에서 '한과장'을 고르면
- Then: 그 카드만 '배정'으로 바뀌고 "담당: 한과장"과 [완료] 버튼이 보인다. [완료]를 누르면 '완료'(초록)로 바뀐다
- (테스트: "배정하면 200 · 상태가 '배정'" · "완료하면 200 · 상태가 '완료'" · "없는 번호 404" · "상태에 목록 밖의 값을 보내면 400")

### AC-05 저장 (US-05)
- Given: 신고를 1건 등록한 뒤
- When: 서버를 껐다가(Ctrl+C) 다시 켜면
- Then: 그 신고가 목록에 그대로 있다
- (눈으로 확인: Supabase는 Table Editor · SQLite는 `npm run peek`. 테스트는 진짜 DB를 건드리지 않으므로 이 기준은 사람이 확인)

## 8. 우선순위 (MoSCoW)와 범위 밖

- **Must**: US-01 목록 · US-03 신고 · US-04 처리 · US-05 저장
- **Should**: US-02 상태 필터
- **Could**: 카드에 설비 번호 표시 · 건물별 색 구분
- **Won't (오늘 안 함)**: 아래 표

| 만들지 않을 것 | 이유 |
|---|---|
| 로그인 · 권한(역할 구분) | 이번 서비스 범위 밖. 회사에서 쓰려면 사내 SSO를 붙여야 함(8일차 M3에서 다룸) |
| 심각도 직접 고르기 | 8일차 M1에서 AI가 제안하고 사람이 [승인]하는 방식으로 붙임. M2 미션 ②에서 AI 제안이 있거나 보류된 카드에 한해 붙임 (10.3절) |
| 신고 삭제 · 내용 고치기 | 기록은 지우지 않음 |
| 사진 첨부 · 알림(메신저 · 메일) | 오늘 범위 밖 |
| 회원가입 · 내 신고만 보기 | 로그인이 없으므로 해당 없음 |

## 9. AI 수습 평가 기준 (8일차 M1)

AI는 시설팀에 새로 들어온 **수습 직원**입니다. 신고를 보고 심각도(4절)와 유형(6절 `category`)을 **제안**만 하고, 확정은 시설팀이 [승인]으로 합니다.
아래 다섯 가지를 모두 지켜야 수습을 통과합니다. M1 실습(1-2~)의 AC-06~는 이 기준을 하나씩 확인하는 방법입니다.

| # | 기준 | 통과 조건 | 예 |
|---|---|---|---|
| 9-1 | 정확 | 4절 기준대로 심각도를 제안한다 · 사람이 다칠 수 있으면 긴급 | "2층 천장에서 물이 샙니다" → 긴급 |
| 9-2 | 정해진 답만 | 심각도는 `urgent` · `warning` · `info` 중 하나, 유형은 `ELECTRIC` · `HVAC` · `IT_DEVICE` · `BUILDING` 중 하나. 그 밖의 답은 서버가 버린다 | "매우 긴급" · `PLUMBING` → 버림 |

### 9.1 자동 분류 + [승인] (1-2)

| 하는 일 | 주소 | 성공하면 | 실패하면 |
|---|---|---|---|
| AI 분류 제안 받기 | `POST /api/reports/:id/classify` | **200** + 제안이 담긴 신고 | 없는 번호 **404** · AI가 멈추거나 답이 규칙 밖이면 **503** `AI_UNAVAILABLE` |
| 제안 승인 | `POST /api/reports/:id/approve` | **200** + 심각도 · 유형이 제안대로 바뀐 신고 | 없는 번호 **404** · 제안이 없으면 **409** `CONFLICT` |

- 제안은 `reports`에 칸 세 개를 더해 저장한다: `ai_severity`(`urgent` · `warning` · `info` · 빈칸) · `ai_category`(4가지 유형 · 빈칸) · `ai_reason`(이유 한 문장 · 빈칸). 테이블은 `003_ai.sql`로 바꾼다.
- 제안을 받아도 `severity` · `category`는 그대로다. [승인]을 눌러야 제안이 그 칸으로 옮겨진다 (9-4).
- AI 답은 서버가 검사한다(`checkAiResult`). 목록 밖 값이 하나라도 있으면 제안 전체를 버리고 503 (9-2).
- 화면: 신고를 보내면 그 신고의 AI 분류를 자동으로 요청한다. 카드에는 "AI 제안: (배지) 이유"와 [승인]이 보인다. 아직 제안이 없는 미분류 카드에는 [AI 분류] 버튼이 있다.

- AI가 정하기 어려우면 제안에 **판단 보류**(`ai_hold`)가 붙는다. 보류 카드는 [승인] 대신 사람이 심각도를 직접 고른다 (M2 미션 ① · 10.2절).

### 9.2 담당 추천 · 도구 (1-3 · 미션)

AI가 **도구(tool)**로 사실을 직접 조회한 뒤 담당자를 추천합니다. 도구는 **조회만** 하고 아무것도 바꾸지 않습니다. 추천은 저장하지 않고, 배정은 사람이 담당 고르기로 합니다 (9-4).

| 하는 일 | 주소 | 성공하면 | 실패하면 |
|---|---|---|---|
| 담당 추천 받기 | `POST /api/reports/:id/recommend` | **200** + `{ assignee, reason, asset_advice, tools }` | 없는 번호 **404** · AI가 멈추거나 답이 규칙 밖이면 **503** `AI_UNAVAILABLE` |

| 도구 | 하는 일 | 돌려주는 것 |
|---|---|---|
| `get_handler_load` | 담당자 4명의 지금 일 양 | 이름 · 분야 · 맡고 있는 '배정' 신고 수 |
| `get_asset_history` (미션) | 설비 번호 하나의 이력 | `data/assets.json`의 설비 정보 · 지난 수리 + 같은 설비 번호의 신고 목록 · **최근 7일 신고 수** |

- 분야: 전기 이주임 · 공조 최대리 · IT기기 정사원 · 건물 한과장 (2절). 유형에 맞는 사람을 먼저 보고, 일 양을 이유에 쓴다.
- **"최근 7일"의 기준 시각은 그 신고가 접수된 시각**이다. 그 시각부터 7일 전까지(그 신고 포함) 같은 설비 번호의 신고를 센다. 실습 데이터(11/17~24)가 수업 날짜와 달라도 같은 결과가 나온다.
- `asset_advice`: 설비 번호가 없으면 빈칸. 있으면 `수리` 또는 `교체 검토`. **최근 7일 신고 3건 이상이거나 내용연수가 지났으면 `교체 검토`**.
- `tools`는 서버가 실제로 실행한 도구 이름이다 (AI가 말한 것이 아님).
- 서버 검사(`checkRecommendResult`): `assignee`는 4명 중 하나 · `reason`은 빈칸이 아님 · `asset_advice`는 위 세 값 중 하나. 아니면 버리고 503.

### 9.3 안내문 스트리밍 (1-4)

시설팀이 신고 장소 주변 직원에게 보낼 안내문을 AI가 **초안**으로 씁니다. 글자는 받는 대로 화면에 흘러나오고, 사람이 고친 뒤 [보내기]를 눌러야 저장됩니다.

| 하는 일 | 주소 | 성공하면 | 실패하면 |
|---|---|---|---|
| 안내문 초안 받기 | `POST /api/reports/:id/notice/draft` | **200** + 글자 조각이 차례로 오는 `text/plain` (저장 안 함) | 없는 번호 **404** · AI가 시작하지 못하면 **503** `AI_UNAVAILABLE` · 중간에 끊기면 연결이 끊김 |
| 안내문 보내기 | `POST /api/reports/:id/notice` | **200** + `notice`가 저장된 신고 | 빈 안내문 · 1000자 넘음 **400** · 없는 번호 **404** |

- **안전 문구는 AI가 쓰지 않고 서버가 정해 둔 문장**을 초안 맨 앞에 붙인다. 승인된 심각도(`severity`)가 긴급일 때만 붙는다.
  - 긴급: `[안전] 해당 장소에 가까이 가지 마시고, 시설팀이 도착할 때까지 주변 사람들이 멀리 돌아가도록 해 주세요.`
- AI는 무엇이 고장 났는지 · 어디를 피하면 되는지 · 시설팀이 처리 중이라는 것만 짧게 쓴다. 안전 행동 지시는 쓰지 않는다.
- 저장은 `reports.notice` 칸(`004_notice.sql`, 1000자 이하 · 기본 빈칸). 초안을 받는 것만으로는 아무것도 저장되지 않는다.
- 화면: 완료가 아닌 카드에 [안내문]. 누르면 글 칸이 열리고 초안이 흘러나온다. 끊기면 받은 글은 그대로 두고 "중간에 끊겼어요"를 보인다. 글 칸은 고칠 수 있고 [보내기]로 저장한다. 보낸 안내문은 카드에 보인다.

- Then: 맨 앞에 서버 고정 안전 문구가 나오고 AI 글이 조각조각 흘러나온다. 중간에 끊겨도 받은 글은 남는다. [보내기] 전에는 저장되지 않고, 보내면 카드에 안내문이 보인다
- (테스트: "AI가 멈추면 안내문 초안 503 · 아무것도 저장 안 됨" · "안내문 보내기 200 · 빈칸 · 1000자 넘으면 400" · "안전 문구는 긴급일 때만 서버 고정 문장")

### 9.4 고장 주입 (1-5)

AI가 실제로 고장 나기 전에, 일부러 고장을 내 보고 서비스가 버티는지 확인합니다 (9-5). `.env`나 터미널에 `AI_FAULT`를 넣으면 서버가 Claude를 부르지 않고 그 고장을 흉내 냅니다.

| `AI_FAULT` | 흉내 내는 고장 | 서버가 하는 일 |
|---|---|---|
| `auth` | 키가 틀림 (Claude가 401) | 503 `AI_UNAVAILABLE` |
| `slow` | 답이 오지 않음 | `AI_TIMEOUT_MS`(없으면 기능별 기본값)가 지나면 포기 → 503 |
| `empty` | 답이 비어 있음 | 503 |
| `refusal` | AI가 답을 거절함 (`stop_reason: refusal`) | 503 |

- 어떤 고장이어도 **신고는 201로 접수**되고 신고 내용은 바뀌지 않는다. AI 기능(분류 · 담당 추천 · 안내문 · 챗봇 · 미식 추천)만 503이다.
- 목록에 없는 `AI_FAULT` 값도 고장으로 본다(503). 서버는 켤 때 `AI_FAULT`가 있으면 터미널에 경고를 찍는다.
- **실습이 끝나면 `AI_FAULT`를 지운다.** 테스트는 서버를 켤 때만 `AI_FAULT` · `AI_TIMEOUT_MS`(짧게)를 준다.

### AC-11 고장 주입 4종 (1-5)
- Given: `AI_FAULT`가 `auth` · `slow` · `empty` · `refusal` 중 하나일 때
- When: 신고를 하고 AI 분류 · 담당 추천을 요청하면
- Then: 신고는 201이고 미분류 · 접수 그대로, AI 요청은 503 `AI_UNAVAILABLE`이다. `slow`는 `AI_TIMEOUT_MS` 안에 포기한다
- (테스트: `tests/fault.test.js` "고장 주입 auth/slow/empty/refusal: AI는 503이어도 신고는 201")

### 9.5 FAQ 챗봇 (1-6)

직원이 "신고는 어떻게 해요?" 같은 질문을 하면 AI가 **`data/faq.json`의 FAQ만 근거로** 답합니다. 대화는 저장하지 않고 화면 메모리에만 있습니다.

| 하는 일 | 주소 | 성공하면 | 실패하면 |
|---|---|---|---|
| 챗봇에게 묻기 | `POST /api/chat` | **200** + `{ answer, sources: [{ id, q }] }` | 대화 모양이 규칙 밖이면 **400** `BAD_INPUT` · AI가 멈추거나 답이 규칙 밖이면 **503** `AI_UNAVAILABLE` |

- **1턴 = 메시지 한 개**(사용자 질문 하나 또는 AI 답 하나). 화면은 대화 전체를 `messages: [{ role, content }]`로 보낸다.
- 서버 검사(400): `messages`가 배열이 아니거나 비어 있음 · **21개 이상** · `role`이 `user` · `assistant`가 아님 · `content`가 빈칸이거나 500자 넘음 · 마지막 메시지가 `user`가 아님.
- **AI에게는 최근 10턴만 보낸다**(`chatWindow`). 잘라 낸 첫 메시지가 `assistant`이면 하나 더 빼서 `user`로 시작하게 한다 (API가 `user` 시작을 요구함).
- 화면은 메시지가 20개가 되면 입력을 끄므로 21개 검사는 화면 밖에서 직접 보낼 때를 막는 장치다.
- **FAQ 근거**: AI는 system에 넣은 FAQ만 쓰고 `{ answer, faq_ids }`로 답한다. FAQ에 없는 질문이면 `faq_ids`를 비우고 시설팀에 문의하라고 답한다.
- 서버 검사(`checkChatResult`): `answer`가 빈칸이 아니고 `faq_ids`가 모두 FAQ에 있는 번호일 때만 통과. 아니면 버리고 503. `sources`는 서버가 FAQ에서 찾아 채운 값이다 (AI가 말한 질문 글이 아님).
- 화면: 신고함의 [FAQ 챗봇] 버튼을 누르면 창이 열린다(처음에는 닫힘). 말풍선 · AI 답 아래 "근거: FAQ n. 질문" · 입력 칸 · [보내기] · [새 대화] · 안내 "AI에게는 최근 10턴만 보냅니다". 오류는 창 안에 한국어로 보이고 대화는 남는다.

### AC-12 FAQ 챗봇 (1-6)
- Given: 신고함 화면에서
- When: [FAQ 챗봇]을 열고 "천장에서 물이 새면 누가 처리해요?"를 물으면
- Then: FAQ에 근거한 답과 "근거: FAQ n. 질문"이 보인다. FAQ에 없는 질문이면 근거 없이 시설팀 문의를 안내한다. 메시지가 21개 이상이면 400이고, AI는 최근 10턴만 받는다. AI가 멈추면 503이고 신고는 그대로다
- (테스트: `tests/chat.test.js` "챗봇: 21턴 이상이면 400" · "챗봇: 잘못된 대화 모양이면 400" · "챗봇: AI에게는 최근 10턴만 보낸다" · "챗봇: AI가 멈추면 503 · 신고는 그대로" · "챗봇 답 검사: FAQ에 없는 번호 · 빈 답이면 버린다" · "챗봇 창은 처음에 닫혀 있다")

### 9.6 usage 표 (1-7 · 시연)

강사가 화면 대신 터미널에서 돌리는 시연입니다. 신고 분류를 진짜 Claude로 몇 번 불러 **토큰 사용량**과 **effort를 낮춰도 분류가 같은지**를 표로 보이고, 9일차 운영비 계산의 근거로 씁니다. 서버 · 화면 · DB는 바뀌지 않습니다(서버의 분류는 지금처럼 effort `low`, 캐시 없음).

- 실행(사내망): `node --use-env-proxy --use-system-ca --env-file=.env eval/usage_demo.js` (사내망 밖은 앞의 두 옵션 없이). 진짜 호출이라 비용이 든다(신고 8건 × effort 2가지 = 16번).
- 신고 8건: `data/seed.json`에서 심각도가 정해진 신고 중 긴급 2 · 주의 3 · 정보 3건. 나머지 12건은 **참고 사례**로 system 뒤에 붙인다(시연 신고의 정답이 새지 않게 겹치지 않는다).
- **캐시**: system(분류 기준 + 참고 사례)에 `cache_control`을 붙인다. 같은 앞부분이 다시 오면 캐시 읽기(`cache_read_input_tokens`)로 싸게 읽힌다. 캐시는 앞부분이 최소 길이(512토큰, 문서 기준) 이상이어야 걸려서 참고 사례를 붙였다. 그래서 비교표는 서버의 `CLASSIFY_SYSTEM` 그대로가 아니라 **"CLASSIFY_SYSTEM + 참고 사례"**로 잰 값이다.
- **순서**: effort를 바꾸면 캐시가 깨질 수 있어 `high`를 8건 모두 돌린 뒤 `low` 8건을 돌린다.
- ① usage 표: 호출마다 `input` · 캐시 쓰기 · 캐시 읽기 · `output` 토큰과 합계. ② 분류 비교표: 건마다 high · low의 심각도 · 유형과 같음 여부(심각도와 유형이 **둘 다** 같아야 같음, 이유 문장은 달라도 됨)와 "같음 n/N".
- 토큰 수만 남긴다. 가격은 바깥 사실이라 이 스크립트에서 계산하지 않는다.

## 10. M2 수습 평가 (8일차)

AI를 믿어도 되는지 **평가셋**으로 숫자로 확인하고(10.1), AI가 모를 때는 모른다고 하게 하고(10.2), 사람이 고친 건을 평가셋 후보로 모읍니다(10.3).

### 10.1 평가셋과 `run_eval` (2-1)

- `eval/golden.json`: 평가셋 10건. 시설팀 선임이 4절 기준으로 정한 정답 심각도(`expected`)와 이유(`why`)가 있다. 시드의 미분류 신고에서 골랐고 애매한 건(타는 냄새 + 더움 · 엘리베이터 덜컹 · 콘센트 따뜻함 등)이 섞여 있다. 모양: `{ note, items: [{ id, title, location, building, asset_id, body, expected, why }] }` (`id`는 시드 번호를 참고로 적은 값).
- `eval/run_eval.js`: 서버를 `DB_MODE=memory`로 잠깐 켜고(진짜 DB는 건드리지 않음) 건마다 `POST /api/reports`로 신고를 만든 뒤 `POST /api/reports/:id/classify`로 분류해 채점한다. **진짜 Claude를 부른다(10번, 비용이 듦).**
- 실행(사내망): `node --use-env-proxy --use-system-ca --env-file=.env eval/run_eval.js`
- 표: 번호 · 제목 · 정답 · AI · 맞음 · 보류. 요약: 정확도 n/10 · 보류 n건 · 틀린 건 중 보류로 걸러진 수 · 보류를 빼고 본 정확도.
- 키가 없거나 서버가 안 켜지면 한국어 한 줄을 찍고 종료 코드 1로 끝난다.

### AC-E1 평가 정확도 표 (2-1)

- Then: 건마다 정답 · AI 제안 · 맞음 · 보류가 표로 나오고 "정확도 n/10"이 찍힌다. AI가 멈춰 503이면 그 건은 미분류로 틀린 것으로 센다
- (테스트: `tests/eval.test.js` "AC-E1 평가 채점: 정답과 같으면 맞음 · 503이면 미분류로 틀림" · "AC-E1 키가 없으면 평가는 한국어 안내로 끝난다". 진짜 평가 결과는 사람이 돌려 보고 HANDOFF.md에 적음)

### 10.2 판단 보류 (미션 ①)

- **"모르는 것"의 기준**: 심각도나 유형을 하나로 정할 근거가 모자란 경우다 — 두 분야에 걸쳐 있거나(예: 더운데 타는 냄새) 위험한지 알 수 없을 만큼 짧을 때. 이때 AI는 `needs_human: true`를 낸다(심각도 · 유형 · 이유는 늘 같이 낸다).
- **어느 쪽으로 기울까**: 보류인데 제목이나 내용에 **안전 단어**가 있으면 서버가 제안 심각도를 `urgent`로 올린다. 안전 단어(고정 목록, `src/ai.js`의 `SAFETY_WORDS`): 타는 · 탄 냄새 · 연기 · 불꽃 · 스파크 · 누수 · 물이 새 · 물이 떨어 · 가스 · 감전 · 흔들 · 넘어 · 비상구. 보류가 아닐 때는 쓰지 않는다.
- **보류 상한**: 평가셋 10건 중 **3건 이하**. 넘으면 "보류 상한 초과"로 보고 표가 알린다(너무 많이 보류하면 AI를 쓰는 의미가 줄어듦).
- 서버 검사(`applyHold`): `needs_human`이 없으면 보류 아님 · `true`면 보류 · `false`면 보류 아님 · boolean이 아닌 값이면 제안 전체를 버리고 503(9-2와 같은 원칙). 순서는 `checkAiResult` → `applyHold` → 저장.
- 보류 여부는 `reports.ai_hold`(0 또는 1, 기본 0, `005_hold.sql`)에 저장한다.
- 화면: 보류 카드의 AI 줄은 "판단 보류 · 사람 확인 필요 (기운 배지) 이유"이고 심각도 배지는 미분류 그대로다(9-4). **[승인]은 화면에서만 숨긴다**(서버 `approve`는 그대로). 사람은 10.3의 심각도 고르기로 정한다.

- (테스트: `tests/eval.test.js` "AC-18 판단 보류: 보류이고 안전 단어가 있으면 긴급으로 올린다" · "AC-18 판단 보류: 안전 단어가 없으면 AI 심각도 그대로 · needs_human이 없으면 보류 아님 · 이상한 값이면 버린다" · "AC-18 보류 상한 이하: 10건 중 보류 3건까지만 통과로 본다")

### 10.3 현장 수정 → 평가셋 후보 (미션 ②)

- **사람이 심각도를 정하는 길**: `PATCH /api/reports/:id`가 `severity`(`urgent` · `warning` · `info`)를 받는다. 그 밖의 값은 **400** `BAD_INPUT`. 화면은 AI 제안이 있거나 보류된, 완료되지 않은 카드에 "심각도 (고르세요)"를 둔다. 고르면 그 카드만 바뀌고 급한 순으로 다시 놓인다.
- **"고친 것"의 기준**: 사람이 심각도를 정한 신고 중 ⓐ 보류였던 것(`ai_hold=1`) 또는 ⓑ AI 제안과 다르게 정한 것. 제외: [승인]으로 제안 그대로 들어간 것 · 제안과 같은 값을 고른 것 · AI 제안이 없던 것 (앞의 두 제외는 보류가 아닌 건에만 적용 — 보류였던 건은 사람이 같은 값을 골라도 남긴다). 지금 있는 칸에서 계산하므로 테이블은 더하지 않는다.
- **후보 보는 곳**: `GET /api/eval/candidates` → **200** `{ items: [{ id, title, location, building, asset_id, body, expected, why }] }`(`golden.json`의 `items`와 같은 모양, `expected`는 사람이 정한 심각도). `why` 예: "현장 수정: AI 제안 주의 → 사람 긴급" · "판단 보류 → 사람 긴급". 후보를 `golden.json`에 자동으로 넣지는 않는다(사람이 보고 옮김).

### 10.5 판단 주체 표시 (2-3 · 현장 피드백 FB-1)

시설팀 박주임: "AI 제안을 승인한 건지 제가 직접 정한 건지 카드에서 구분이 안 돼요. 나중에 '누가 판단했냐'고 물으면 답을 못 합니다."

- 새 칸 `reports.severity_by`(`''` · `ai` · `human`, 기본 빈칸, `006_severity_by.sql`): `ai` = [승인]으로 AI 제안을 받아들임 · `human` = 사람이 심각도 고르기로 직접 정함 · 빈칸 = 아직 안 정함(시드 · 예전 데이터).
- **서버만 정한다.** `POST /api/reports/:id/approve`는 `ai`, `PATCH /api/reports/:id`의 `severity`는 `human`을 서버가 넣는다. `PATCH`에 `severity_by`를 보내면 무시하지 않고 **400** `BAD_INPUT`으로 거절한다(화면이 "AI 승인"으로 위장하지 못하게).
- **이미 심각도가 정해진 신고는 [승인]이 409**("이미 심각도가 정해진 신고입니다"). 사람이 정한 심각도를 승인 주소로 AI 제안이 덮어쓰고 판단 주체까지 `ai`로 바뀌는 길을 막는다(테스트 뚫기에서 찾음). 규칙은 `src/judge.js`의 `approveFields`.
- 화면: 심각도가 정해진 카드의 위치 줄 끝에 "판단: AI 제안 승인" 또는 "판단: 시설팀 직접". 빈칸이면 아무것도 보이지 않는다. 평가셋 후보(10.3) 모양은 그대로다(`severity_by`를 넣지 않음).

## 11. 배포 (M3 3-1)

이 서비스를 Vercel에 올려 휴대폰으로 열어 보는 준비입니다. 올리는 방법과 사용자가 할 일은 `docs/DEPLOY.md`에 있습니다. **실제 배포는 크루가 하지 않습니다**(GitHub · Vercel 계정 작업과 환경변수 값 입력은 사용자 몫).

- **입구 함수**: `src/server.js`가 요청 하나를 처리하는 함수 `handle(req, res)`를 내보내고(`export default`), 서버를 켜는 일은 `start()`로 따로 둔다. import만으로는 서버가 켜지지 않는다. 루트 `server.js`는 로직 없이 `if (import.meta.main) start();`와 `export default handle;`뿐이다.
  - `node server.js` · `npm start` · 고정 테스트: 직접 실행이므로 지금처럼 서버가 켜진다.
  - Vercel: 루트 `server.js`가 기본으로 내보낸 함수만 입구로 쓴다. 화면 · API · 스트리밍 안내문이 모두 같은 `handle`을 지나므로 로컬과 처리가 같다.
- **`vercel.json`**: 서울 리전 `icn1`만 둔다.
- **SQLite**: Vercel의 함수 폴더는 쓸 수 없으므로 `VERCEL` 환경변수가 있으면 `db.js`가 SQLite 파일을 임시 폴더(`os.tmpdir()`의 `app.db`)에 둔다. 서버마다 따로 있어 데이터가 시드로 돌아간다(관찰 ①). 이 일은 `db.js`만 안다.
- **올라가면 안 되는 파일**: `.env` · `.env.*` · `data/app.db*`. `.gitignore`와 `.vercelignore`에 함께 둔다. GitHub 웹 업로드는 `.gitignore`를 따르지 않으므로 DEPLOY.md가 올릴 파일 목록을 따로 적는다.
- **키는 화면에 없다**: `src/public/` 안에 서버 전용 키 이름이나 값이 없어야 한다. Supabase는 서버 전용 키(`SUPABASE_SECRET_KEY`)만 쓴다.
- AI 키가 없으면 AI 기능만 503이고 신고는 된다(replay 모드는 없음).

- When: 입구 함수를 서버에 꽂아 화면과 API를 부르면
- Then: 화면(200 html)과 `/api/reports`(200 · 40건)가 같은 함수로 나온다. import만으로는 서버가 켜지지 않는다. `src/public`에 키가 없고, `.env` · `data/app.db`는 올리지 않는 목록에 있으며, Node는 `24.x` · 리전은 `icn1`이고, Vercel에서는 SQLite 파일이 임시 폴더에 놓인다
