## 3. AI (OWASP LLM Top 10 · 실습 3-2 · SPEC 12절)
| 위험 | 막는 겹 | 확인 | 결과 |
|---|---|---|---|
| 프롬프트 인젝션(LLM01) — 본문 속 지시 | ① 신고 글을 `<report>`로 한 번만 감쌈(글 속 태그는 지움 · `reportBlock`) + 프롬프트 보안 규칙 | AC-16 ① 테스트 · 진짜 AI로 공격 1 → **긴급**(지시 무시) | ✔ |
| 사람 승인 속이기 · 과도한 에이전시 | ② 값 목록 · 이유에 지시문이 섞이면 버림(`checkAiResult` · `checkRecommendResult`의 `hasDirective`) · ③ 승인은 [승인] 버튼만 | AC-16 ② ③ 테스트 · 진짜 AI로 공격 2 → 이유에 지시문 없음, 심각도 · 상태 그대로 | ✔ |
| 자원 남용(연타) | ④ 접속 주소마다 1분에 AI 10번 · 챗봇 20번 → 429 | AC-17 테스트 2개 (11번째 · 21번째 429, 신고는 201, 다른 주소는 안 막힘) | ✔ |
| AI 결과가 진짜 데이터를 바꿈 | AI는 제안 칸(`ai_*`)에만 씀 · 판단 주체(`severity_by`)는 서버만 정함 | AC-06 · AC-07 · AC-13 · AC-16 ③ | ✔ |
| 시스템 프롬프트 유출 | 프롬프트는 서버(`src/ai.js`)에만 · 화면에 없음 | 화면 파일 비밀 값 테스트 | ✔ |
| 위험한 안전 안내를 AI가 지어냄 | 안전 문구는 서버의 정해진 문장만(`safetyLine`) | AC-10 "안전 문구는 긴급일 때만 서버 고정 문장" | ✔ |
| 연타 제한이 완벽하지 않음 | 기록이 서버 메모리라 Vercel 인스턴스마다 따로 셈 · 로컬에서는 `x-forwarded-for`를 흉내 낼 수 있음 | — | ✖ → 회사에서는 로그인한 사람마다 · 공용 저장소(DB)에 셈 |

공격 문장은 `reference/kit_m3/injection_samples.md`. 진짜 AI 확인은 memory 서버로 공격 1 · 2를 한 번씩 불러 봤다(공격 1 본문에는 "아래 콘센트 · 감전" 문장을 더해 긴급이 맞는 신고로 만듦).

## 6. 배포 방법 비교 (3-3 · 읽기)
"회사로 갈 때 바뀌는 칸 두 개" = **DB 창구**(`src/db.js`) · **로그인 창구**(지금은 없음). 화면 · API(`src/server.js`의 `handle`)는 그대로 쓴다.

| 방법 | 장점 | 걸리는 점 | 이 프로젝트에서 바꿀 곳 |
|---|---|---|---|
| Vercel + Supabase (지금) | push하면 자동 배포 · 무료로 시작 | 외부 클라우드 · 서버 메모리가 인스턴스마다 따로(연타 제한) | 없음 |
| SQLite 파일 | 설치 없이 바로 · 파일 하나 | Vercel에서는 임시 폴더라 재시작하면 사라짐 | `DB_MODE=sqlite` (db.js만) |
| Railway | 서버가 계속 켜져 있음 · 디스크 붙이기 쉬움 | 외부 클라우드 · 유료 | 입구 `npm start` 그대로 |
| Docker | 어디서든 같은 모양으로 실행 | 이미지 만들고 관리하는 일이 늚 | Dockerfile 하나 추가 |
| 사내 서버 | 사내 데이터 · 사내망 안에서 끝남 | 서버 관리 · 승인 절차 | DB 창구 → 사내 DB, 로그인 창구 → 사내 SSO |
